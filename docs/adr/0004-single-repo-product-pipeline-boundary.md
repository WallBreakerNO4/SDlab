# 单仓库承载产品与内部生产线，不做仓库拆分

> 状态：accepted

本仓库同时托管面向用户的网站（产品主体）与作者自用的生图流水线（内部工具）。决定保持单一仓库，用文档把两者显式表述为"一个产品 + 一条内部生产线 + 契约区"，而不是拆成两个 Git 仓库。理由：两侧在代码与构建层面零耦合，唯一硬耦合是 Supabase 表结构、R2 布局与命名约定组成的数据契约——拆仓不会消除它，只会把它变成需要版本化与跨仓同步的可执行工件，并把跨边界改动变成两个有先后的 PR、两次 agent 会话；而当前不存在仓外消费者、独立发布或权限隔离需求，且维护方式依赖 coding agent 在根目录通读全仓，拆分会让上下文与文档维护成本翻倍。曾出现 agent 误判仓库重点（把脚本当主体、把网站当附属）的实际案例，其根因是文档缺少身份表述，而不是缺少物理隔离。

## Considered Options

- 双仓库（polyrepo）：拒绝。需要先建跨仓契约基础设施（版本化 / 校验 / 发布流水线），对单人 + agent 的工作流是净负担；没有仓外消费者与独立发布需求支撑。
- 同仓分目录大搬迁（如 `web/` + `pipeline/`）：拒绝。要动 Next 配置、路径与测试，成本高；agent 固定在根目录启动，搬迁无法阻止其同时看到两侧；结构命名不是问题根因。
- 仅靠口头 / 临时约定维持现状：拒绝。实际误判已发生过，会复发。

## Consequences

- 边界依靠文档与约定维持（`README.md`、根 `AGENTS.md`、`scripts/AGENTS.md`、`data/AGENTS.md`），没有物理隔离。
- 契约区（`supabase/`、`data/` 分账、`docs/`、`CONTEXT.md`）是两侧共享面，变更须两侧一起过；契约常量的镜像漂移风险另见 #6，守卫决策见 [ADR 0005](0005-contract-constant-consistency-guards.md)。
- 出现以下信号时重新评估拆仓：需要把网站单独作为作品展示或开源（当前整仓已公开）、脚本需要私有化、出现仓外使用者、两侧出现真正的独立发布或权限 / 密钥隔离需求、仓库规模增长导致 agent 导航困难。

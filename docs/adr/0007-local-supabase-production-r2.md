# 本地 Supabase + 生产 R2 的两阶段发布

> 状态：accepted

数据库改动长期直接推远端生产库、在线上看效果，没有本地验证环节；而 R2 是内容寻址存储，重复写入天然幂等，完整复刻它的收益远低于成本。因此把本地开发环境限定为「只复刻数据库」：本地 Supabase 栈承载从生产库导出的数据副本，R2 全程指向生产。发布流程由此分成两个阶段——本地开发阶段用 `--local` 把数据库写入指向本地库、资源仍真实上传到生产 R2；验证满意后进入远端同步阶段，先应用迁移，再以默认方式重跑发布，R2 全部命中已存在对象而跳过，只把数据写入远端库。两个阶段的行为差异只体现在数据库目标上，同一份发布逻辑不因阶段分叉。

删除类操作在本地开发阶段有独立的安全语义：本地库是生产库的镜像，删除镜像行不应影响生产对象，因此 `--local` 下只删除本地数据库的行、跳过全部 R2 删除并打印提示。上传类操作则相反——R2 指向生产、照常幂等写入，因为内容寻址对象被多个数据库目标共享是这套设计成立的前提。

## Considered Options

- 全隔离本地 R2（MinIO 等 S3 兼容存储）：拒绝。要复刻 bucket 划分、公开/私有访问、CDN 语义与既有对象，成本远高于收益；而内容寻址 + `head_exists` 幂等让「本地库 + 生产 R2」天然安全。
- 继续直接写远端库、不建本地环境：拒绝。schema 变更没有验证环节，出错即影响生产且撤回困难，这是本决策要偿还的债务。
- 两个阶段各自维护一套发布逻辑：拒绝。行为差异只应存在于数据库目标，逻辑分叉会让两阶段逐渐漂移。
- 本地阶段删除时连带清理生产 R2：拒绝。本地库是镜像，镜像行不代表生产对象的所有权；一次误删不可恢复。
- 为本地登录导出 auth schema 或伪造 session：拒绝。远端密码哈希在本地 GoTrue 下不可解密，网站登录 UI 也只有 OAuth 入口；本地登录走本地栈 GitHub OAuth，产生「本地登录身份」后回填用户数据归属。

## Consequences

- `--local` 覆盖上传、删除、回填三个脚本；env 由 `scripts/env_loading.py` 先加载 `.env.local-db`（只接受数据库键并覆盖进程残留的远端连接变量），再由 `.env` 补漏其余机密。文件缺失时报配置错误，绝不静默回退远端。
- 默认（不带旗标）路径逐字保持既有行为，既有命令与肌肉记忆零回归。
- 数据库侧撤回只需本地 `db reset`（重放迁移 + 种子）；R2 侧无需撤回，内容寻址对象可被后续发布复用。
- 发布顺序固定为「不可变资源 → Supabase 数据 / `run_view_index` → 可变 `view/current.json`」，远端同步阶段因此不会出现「指针已指、数据未写」的窗口。
- 核验点（网站快照的权威来源）：首页目录读 `run_list_items`、媒体授权读 `run_view_index`，二者以数据库为准；但模型详情页的数据入口是共享 R2 的 `view/current.json`。原假设「指针覆盖不应立即影响生产」在核验后不成立：本地开发阶段发布仍会覆盖生产指针，使生产详情页指向本地快照，登录用户还会因 `access.release_id` 与指针不一致而报错。该影响不改变首页目录与授权，但意味着两阶段应成对执行：本地验证结束后跑一次远端同步阶段把指针写回生产快照；对已发布评测做本地发布时，详情页错位会持续到下一次远端同步阶段。
- 本地开发阶段每次 `db reset` 都会清空 auth schema，本地登录身份需重新登录并重跑归属回填 SQL；该流程文档化在 `supabase/AGENTS.md`，不做成脚本。
